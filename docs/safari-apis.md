# MegaApp Safari / iPad capability research

Checked 2026-09-30. Scope: creative editors, games, local persistence, and an optional cloud or Mac connection. This is a bounded audit of capabilities that could matter to MegaApp, not a claim that every web platform API is integrated. Sources are Apple/WebKit release notes, MDN reference pages, standards, and the MDN browser-compat-data repository. Safari 27.0 is documented as released on September 17, 2026; the user's actual iPad model, Pencil, keyboard, and iPadOS version are still unknown. [Safari 27.0 release](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)

## Recommended first release

Ship a static HTTPS app shell, a manifest and Home Screen instructions, a versioned offline service-worker cache, a drawing/input laboratory, and a small typed variable store. Save the sample store in IndexedDB (or localStorage for a deliberately tiny demonstration), with a schema version and explicit JSON import/export. It should include namespaced text, number, boolean, and JSON values. Do not present this demonstration as cloud synchronization, a permanent backup, or a secure credential vault.

The drawing lab should accept fingers, Pencil, mouse, and trackpad through Pointer Events. Record actual pressure, tilt, altitude/azimuth, contact geometry, buttons, coalesced sample count, predicted sample count, and whether useful values were observed. Render at the measured devicePixelRatio, handle container resize, offer undo/clear/export, and preserve enough stroke data to redraw after a resize. Predicted positions should be temporary previews rather than committed stroke geometry.

Provide a capability page with three different notions of status: API exposed, operation successfully attempted, and permission or context required. A binary property check does not establish that the hardware exists or that an operation will succeed. Do not automatically request microphone, camera, location, clipboard reading, motion, or notifications. Put each behind a clear action, record actual errors, and stop/release resource handles when its test ends.

## Decisions to raise only when necessary

1. **Installed app or ordinary Safari tab as the everyday workspace:** recommend installation, because storage is separated. Manual export/import bridges the first version. Cloud sync should reconcile independently owned local copies later.
2. **Is sample state allowed to be evicted:** yes for this prototype; make import/export visible before real work is valuable. Browser persistence is not the same as keeping a file in iCloud Drive.
3. **Need arbitrary app code or only trusted apps:** same-origin apps can read the same state and imported keys. A future ecosystem of generated code needs explicit sandbox and capability boundaries before secrets are introduced.
4. **Need low-latency local threads or unrestricted external resources:** cross-origin isolation and hosting response headers can become a meaningful hosting decision. Do not impose isolation before a workload needs it.
5. **Need native Pencil gestures or MIDI/hardware I/O:** those may require a native shell or gateway; basic expressive drawing and local music synthesis are already possible without that choice.
6. **Need cloud API credentials:** choose authenticated private proxy later. Do not put credentials in this sample variable store or exported snapshots.
7. **Need sync while app is closed or a persistent agent:** a cloud/Mac process owns that lifetime. The iPad web app cannot promise continuous background execution.

## Device validation checklist for the first feature

- Open the deployed HTTPS URL on the real iPad, then install from Safari and reopen it.
- In each context, create text, numeric, boolean, and JSON sample variables; reload and relaunch to verify round-trip persistence. Verify the contexts are separate rather than implying shared state.
- Export a JSON snapshot, clear sample data intentionally, then import and compare the values. Invalid imports must leave prior data intact.
- Load once online; verify service-worker control; enable airplane mode and relaunch to confirm the shell, drawing surface and variables still work.
- Test Pencil pressure/tilt, finger drawing, two-touch interaction if exposed, mouse/trackpad, keyboard, resize/split view, rotation, undo and PNG share/export.
- Permission tests should accurately distinguish blocked, denied, unavailable hardware, and success; stop mic/camera and sensors after testing.
- No physical iPad or Pencil was controlled in this audit. Desktop browser success cannot substitute for those checks.
