# Safari / iPad creative canvas capabilities

Research checked 2026-09-29. Scope: primary WebKit/Apple documentation, API specifications, MDN reference and MDN's source compatibility data. This records shipping milestones, not a claim that Manny's particular iPad has them. Feature detection, successful context creation, and real-device input observation remain necessary.

## Recommended first implementation

1. Build a 2D canvas precision playground using Pointer Events, with live pressure/angle/contact telemetry, pressure-dependent strokes, a hover cursor, and separate actual/predicted stroke layers.
2. Process every coalesced sample if available; otherwise process the dispatched event. Store actual input only. Draw predictions as temporary feedback, replacing them when actual samples arrive. Predictions can be empty and are not reliable saved geometry.
3. Keep editor coordinates in CSS-pixel units. Size the backing bitmap from the observed element size × devicePixelRatio, and set a matching drawing transform. Recompute on ResizeObserver/viewport changes. Avoid border/padding/transforms on the canvas element itself; use a wrapper.
4. Set pointer capture while drawing and finish safely on pointerup, pointercancel, and lostpointercapture. Limit touch-action:none to the active drawing surface, preserving normal page zoom/scroll elsewhere.
5. Render through requestAnimationFrame; queue samples without rebuilding UI for every event. Keep the document/strokes separate from the bitmap so resizing does not erase the artwork. Use workers/OffscreenCanvas only where workload justifies them.
6. Probe WebGL2 and WebGPU on separate small canvases. Request a WebGPU adapter/device only through a deliberate test action; report unavailable/null/rejected explicitly. Keep Canvas2D available when enhanced rendering cannot initialize.

These are implementation recommendations inferred from the documented API behavior below, not a proposed requirement to build a full editor immediately.

## Coordinate and sampling details

For an unrotated canvas with no border/padding, backing-bitmap coordinates are `(clientX - rect.left) * canvas.width / rect.width` and analogous Y. If rendering uses a DPR transform and document units are CSS pixels, use CSS-local coordinates rather than multiplying by DPR twice. For editor pan/zoom, apply the inverse of the editor view transform after mapping from the viewport. This is an implementation inference from bounding rect + canvas/DOMMatrix coordinate definitions.

For each pointermove, obtain `const samples = event.getCoalescedEvents?.();` and process `samples?.length ? samples : [event]`. Do not process the parent event again after a nonempty sample list. Maintain predicted marks on a separate temporary layer. All geometry should preserve floating-point coordinates. A hardware property that remains zero is not necessarily absent; capability UI should distinguish API present from sensor data observed.

## Significant decisions to surface later

- Is finger input for drawing, or for moving the view while Pencil draws? Either can be a reversible setting first.
- Minimum iPadOS version: 18.2 unlocks coalescing/prediction/orientation; 26 unlocks WebGPU. Initial canvas should fall back without blocking older devices.
- Rendering architecture: Canvas2D is sufficient for the first playground. A full music/game/creative suite may justify GPU or worker renderers; avoid prematurely requiring them.
- Multithreaded compiled engines: hosting with response-header control becomes necessary if adopting Wasm threads. This is a hosting decision, not a local-variable toggle.
- Native Pencil interactions: squeeze, double tap, and haptic feedback require a later native integration decision if they become essential.
